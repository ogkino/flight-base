# 多语言（i18n）开发指南

> **版本**：v1.0（随 v2.6 框架引入）
> **当前支持语言**：简体中文（`zh-CN`，默认）、English（`en-US`）
> **适用范围**：后台管理系统（`public/admin/*`）。前端公开页面（Views）如需多语言，可复用本文档的后端部分（`lang()`），前端部分需自行接入。

---

## 🎯 设计目标

1. **零侵入现有功能**：不改变现有 API 返回结构，只是把硬编码的中文文案替换成 `lang()` / `t()` 调用。
2. **三块拼图，各管各的**：
   - **`CrudConfig.php` 内容**（菜单、表单/表格文案）：用**字段级多语言后缀**（`title_en` 等），就近手写维护，不额外维护语言包。
   - **后端动态消息**（Controller/Middleware 里的成功/失败提示）：用 `lang()` + `app/lang/*.php` 语言包。
   - **前端静态外壳**（登录页、顶部导航、`crud-renderer.js` 通用文案）：用 `t()` + `i18n.js` 字典。
3. **约定优于配置**：新增模块只需要按本文档的写法加 `_en` 字段或调用 `lang()`/`t()`，无需关心底层是如何检测语言的。
4. **优雅降级**：找不到翻译时自动回退到基准语言包（`zh-CN`），最终回退到 key 本身，**永远不会报错或显示空白**，方便在开发期一眼看出漏翻译的 key。

---

## 🧩 整体架构

```
浏览器（localStorage: admin_locale）
   │
   │  config.js: getLocale() / setLocale()
   │  request() 自动附带请求头 X-Locale
   ▼
┌─────────────────────────────────────────┐
│  前端静态外壳（i18n.js）                  │
│  - data-i18n / data-i18n-placeholder     │
│  - t('section.key', '兜底文案')          │
│  - 登录页、顶部导航、crud-renderer.js 通用文案 │
└─────────────────────────────────────────┘
   │  HTTP 请求头：X-Locale: en-US
   ▼
┌─────────────────────────────────────────┐
│  后端（app/helpers/i18n.php）             │
│  - currentLocale() 读取 X-Locale/?lang/Cookie │
│  - localizeConfig() 解析 CrudConfig.php 里的  │
│    title_en 等字段后缀（菜单/表单/表格文案）   │
│  - lang('section.key') 查 app/lang/*.php     │
│    （仅 Controller/Middleware 动态消息使用）  │
└─────────────────────────────────────────┘
```

**语言探测优先级**（后端 `currentLocale()`）：

1. 请求头 `X-Locale`（前端 `request()` 已自动附带，见 `config.js`）
2. 查询参数 `?lang=`（用于 View 模式 / 直接访问的页面）
3. Cookie `admin_locale`（`setLocale()` 会同步写入，供 PHP 渲染页读取，如登录页、View 模式页面）
4. 配置默认值 `app.php` 的 `locale`（当前为 `zh-CN`）

**语言持久化**（前端）：`localStorage.admin_locale` + `Cookie: admin_locale`（双写，前者供 JS 读取，后者供服务端渲染页面读取）。

## 📁 涉及文件一览

| 文件 | 作用 |
|------|------|
| `app/lang/zh-CN.php` | **基准语言包**（简体中文），新增翻译 key 必须先加在这里 |
| `app/lang/en-US.php` | 英文语言包，key 结构必须与 zh-CN.php 完全一致 |
| `app/helpers/i18n.php` | `lang()` / `currentLocale()`（Controller/Middleware 动态消息）+ `localizeConfig()`（解析 CrudConfig.php 的字段后缀） |
| `app/config/app.php` | `locale`（默认语言）、`supported_locales`（支持的语言列表）、`locale_field_suffixes`（字段后缀映射，如 `en-US => en`） |
| `public/admin/assets/js/config.js` | `getLocale()` / `setLocale()`，`request()` 自动附带 `X-Locale` 请求头 |
| `public/admin/assets/js/i18n.js` | 前端字典 `I18N_DICT`、`t()`、`applyI18n()`、`renderLocaleSwitcher()` |
| `public/admin/index.html` | 后台主页：顶部语言切换器 + `data-i18n` 静态文案；`renderMenus()` 渲染分组标题时优先取 `groupConfig.title`（多语言），而不是对象的 key |
| `public/admin/login.html` | 登录页：右上角语言切换器 + `data-i18n` 静态文案 |
| `public/admin/assets/js/crud-renderer.js` | 通用 CRUD 渲染器内置文案（搜索/新增/删除确认等）已改为 `t()` 调用 |
| `app/config/CrudConfig.php` | `getMenus()` / `users()` 是**字段级多语言后缀**（`title_en`/`label_en`/`name_en`）的完整参考示例，其他模块可参照其写法 |
| `app/api/admin/ConfigController.php` | `getPageConfig()` / `getMenus()` 返回前统一调用 `localizeConfig()`；权限过滤后的菜单分组会带上已解析的 `title` 字段 |

## 🔧 后端：如何让新模块支持多语言

**先判断文案的位置，再决定用哪种机制**（这是本框架最核心的约定，请务必先读这条）：

| 文案在哪 | 用什么 |
|---------|--------|
| `app/config/CrudConfig.php` 数组里的文案（菜单、表单 label、表格 title、placeholder、按钮 text……） | **字段级多语言后缀**（`title_en` 等），见下一节，**不要**在这里调用 `lang()` |
| 控制器（Controller）/ 中间件（Middleware）里散落的动态消息（成功/失败提示、校验错误等） | `lang()` + `app/lang/*.php` |

之所以这样分工：`CrudConfig.php` 是"整个文件手写维护"的配置数组，文案和字段本来就写在一起，就近加一个 `_en` 兄弟 key 最省事；而 Controller 里的消息是穿插在业务逻辑代码中的字符串，没有"数组兄弟 key"这个位置，所以维护单独的语言包文件更合适。**两种机制不要混用在同一类内容上**，否则像之前那样——菜单在 `CrudConfig.php` 里已经有 `_en` 写法了，又同时存在于 `lang()` 语言包里——会很混乱。

### CrudConfig.php 里的文案 → 直接看下一节「CrudConfig 字段级多语言」

### 控制器 / 中间件里的动态消息 → `lang()`

第 1 步，打开 `app/lang/zh-CN.php`，在合适的 section 下加一个 key（没有合适的 section 就新建一个，section 名建议用模块名，如 `products`）：

```php
// app/lang/zh-CN.php
return [
    // ... 已有的 common / crud / auth / permission ...

    'products' => [
        'create_success'   => '创建成功',
        'update_success'   => '更新成功',
        'delete_success'   => '删除成功',
        'stock_not_enough' => '库存不足',
    ],
];
```

然后在 `app/lang/en-US.php` 里**用相同的 key 结构**补上英文：

```php
// app/lang/en-US.php
return [
    // ...

    'products' => [
        'create_success'   => 'Created successfully',
        'update_success'   => 'Updated successfully',
        'delete_success'   => 'Deleted successfully',
        'stock_not_enough' => 'Insufficient stock',
    ],
];
```

> ⚠️ **强制约定**：`zh-CN.php` 是基准语言包。`lang()` 找不到某个 key 时会自动回退到 `zh-CN.php`，找不到就直接返回 key 字符串本身（如 `products.stock_not_enough`）——这是故意设计的，方便你在页面上一眼看出"这个 key 忘了翻译"。所以**新 key 一定要先加在 zh-CN.php**，再去 en-US.php 补齐，两边 key 路径必须完全对应。

第 2 步，在控制器里调用：

```php
// app/api/admin/ProductController.php
public static function create()
{
    AuthMiddleware::checkAdmin();
    checkPermission('products', 'create');

    if (getPost('stock') < 0) {
        error(lang('products.stock_not_enough'));
        return;
    }

    $db = db();
    $db->insert('products', [/* ... */]);
    success(['id' => $db->id()], lang('products.create_success'));
}
```

**不是所有文案都必须翻译**：字段技术名（如数据库字段 `sku`）、纯图标类名等不需要翻译。是否翻译取决于该文案是否会展示给最终用户。

### `lang()` 函数签名

```php
lang(string $key, array $replace = [], ?string $locale = null): string
```

- `$key`：点号路径，如 `'products.create_success'`
- `$replace`：占位符替换，文案里用 `:name` 占位，调用时传 `['name' => '张三']`
  ```php
  // 语言包： 'delete_confirm' => '确定删除 :name 吗？'
  lang('products.delete_confirm', ['name' => $product['title']]);
  // => "确定删除 iPhone 15 吗？"
  ```
- `$locale`：一般不传（自动读取当前请求语言），仅用于强制指定语言的场景（如生成多语言邮件模板）

## 🏷️ CrudConfig 字段级多语言（后缀约定）—— 推荐用于业务模块

`lang()` 适合"数量少、可复用"的框架级文案（菜单分组、`common.*`、接口成功/失败消息）。但业务模块的 `CrudConfig.php` 里往往有**大量一次性的字段文案**——每个表单 `label`、表格 `title`、`placeholder`、按钮 `text`……如果每一个都要先去 `zh-CN.php` 加 key、再去 `en-US.php` 补齐、最后回 `CrudConfig.php` 写 `lang('xxx.yyy')`，语言一多（比如 6 种）维护成本会线性爆炸，而且这些 key 基本不会被复用。

**因此针对这类字段级文案，框架提供了更轻量的写法：直接在 `CrudConfig.php` 里给任意 key 加一个语言后缀的"兄弟 key"，不需要碰语言包文件。**

### 写法

```php
'label' => '昵称',
'label_en' => 'Nickname',   // 加一个 {key}_{后缀} 即可
```

后缀对应关系在 `app/config/app.php` 的 `locale_field_suffixes` 里配置：

```php
// app/config/app.php
'locale_field_suffixes' => [
    'zh-CN' => null,   // 默认语言，无需后缀，直接用原 key
    'en-US' => 'en',
],
```

框架会在 `ConfigController::getPageConfig()` / `getMenus()` 返回前，自动调用 `localizeConfig($config)`（`app/helpers/i18n.php`）递归处理整个配置数组：

- 当前语言是 `en-US` 时，任何存在 `xxx_en` 兄弟 key 的 `xxx` 都会被替换为 `xxx_en` 的值；
- **无论最终语言是什么，所有 `_en`（及其他已配置的后缀）结尾的 key 都会从响应里被移除**，前端拿到的 JSON 始终是干净的，不会看到多余字段。
- 这是递归处理的，表单字段、表格列、下拉/单选选项（`options`）、菜单分组的 `items` 等任意嵌套层级都能生效。

### 完整示例

参考 `app/config/CrudConfig.php` 里的 `users()` 方法（已完整改造为双语示例），效果：

```php
public static function users()
{
    return [
        'page' => ['title' => '用户管理', 'title_en' => 'User Management', /* ... */],
        'table' => [
            'cols' => [
                ['field' => 'nickname', 'title' => '昵称', 'title_en' => 'Nickname'],
                [
                    'field' => 'status', 'title' => '状态', 'title_en' => 'Status',
                    'type' => 'select',
                    'options' => [
                        ['value' => '1', 'label' => '正常', 'label_en' => 'Enabled'],
                        ['value' => '0', 'label' => '禁用', 'label_en' => 'Disabled'],
                    ],
                ],
            ],
        ],
        'form' => [
            ['type' => 'input', 'name' => 'nickname', 'label' => '昵称', 'label_en' => 'Nickname'],
        ],
        // ...
    ];
}
```

访问 `GET /api/admin/config?page=users`（带 `X-Locale: en-US`）时，`title`/`label` 等 key 的值会自动变成英文，且响应里不会出现任何 `_en` 字段。

### 什么时候用这个，什么时候用 `lang()`？

**结论：只要文案写在 `CrudConfig.php` 的数组里（包括 `getMenus()`），统一用字段后缀，不用 `lang()`。** `lang()` 只留给 Controller/Middleware 里那些不在任何数组里、穿插在业务逻辑代码中的动态消息（如"库存不足"）。原因很简单：字段后缀就近维护、零额外文件；而 Controller 里的字符串没有"数组兄弟 key"这个位置，只能用语言包。

### ⚠️ 特例：菜单分组标题（数组的 key，不是 value）

`getMenus()` 里每个分组的标题（如"仪表盘"）是 PHP 数组的**key**，而字段后缀约定处理的是**value**（`'label' => 'x', 'label_en' => 'y'` 这种"同一层级、不同 key"的兄弟关系）——key 本身没有"兄弟 key"这个位置，所以 `_en` 后缀不能直接加在 key 上。

**写法**：key 永远保持默认语言不变（这样 `crud-designer.html` 的重命名/删除/拖拽排序等操作都不受影响），在分组的值里加一个普通的 `title` / `title_en` 字段（和 `icon`、`items` 平级），走的还是同一套字段后缀机制：

```php
public static function getMenus()
{
    return [
        '仪表盘' => [                    // key：永远是默认语言，不会随语言切换变化
            'title' => '仪表盘',          // value：用于展示，会被 localizeConfig() 解析
            'title_en' => 'Dashboard',
            'items' => [
                ['name' => '仪表盘', 'name_en' => 'Dashboard', 'page' => 'dashboard', 'icon' => 'layui-icon-home'],
            ],
        ],
        // ...
    ];
}
```

`ConfigController::getMenus()` 和前端 `index.html` 的 `renderMenus()` 渲染分组标题时都优先读 `groupConfig.title`（取不到才兜底用数组 key），所以最终显示的是解析后的多语言文案，不是这个 key。

> ⚠️ **为什么不能用一个按 `currentLocale()` 动态计算 key 的写法？**（历史踩坑记录，之前用过又废弃了）因为 `crud-designer.html` 读取配置是通过 PHP 反射直接**执行** `CrudConfig::getMenus()`（`CrudDesignerController::getConfig()`），如果 key 是 `currentLocale()` 动态算出来的，反射调用的瞬间就会按"当时请求用的是什么语言"塌缩成一个具体字符串，多语言能力当场丢失；设计器保存时还会把这个塌缷结果永久写回文件（就是用户实测遇到的问题：切到英文用过设计器保存一次后，key 直接变成了 `Users`，中文完全丢失）。**必须是纯静态、字面量的数组**（所有语言的值都同时以字符串形式写在文件里）才能在"读取配置 → 设计器编辑 → 保存覆盖文件"这个环节中被完整保留——这也是字段级 `_en` 后缀本身能生效、且能在设计器里存活的根本原因。

### ⚠️ 重要限制

- **只能手写维护，`crud-designer.html` 编辑界面不认识 `_en` / `title` 这些字段**，但因为现在是纯静态数据（不是运行时计算），设计器对分组做"改图标"、"改展开状态"、"改名称"这类操作时，其余未识别的字段（如 `title_en`）大多会被原样保留（设计器内部是就地修改已加载的对象，不是每次都重新构造）。**唯一的例外**：如果通过设计器**重命名**了分组，只有 key 会变，`title`/`title_en` 不会自动跟着改——需要手动去 `CrudConfig.php` 把这两个字段也同步改掉，否则显示的标题会和实际分组不一致。
- 表单/表格里逐个字段的可视化编辑（如新增/编辑一个表单字段）**有更高概率**会丢失 `_en` 后缀（设计器可能是按它认识的 schema 重新构造该字段对象）。保守起见，**任何模块一旦手工加了 `_en` 字段，后续该模块的调整都直接改 `CrudConfig.php` 源码，不要再用设计器保存覆盖**（详见下面 Q6）。
- **后缀替换只在"显式定义了后缀 key"时才会触发**，不会影响任何现有字段。例如表单字段的技术属性 `name`（如 `'name' => 'nickname'`，对应数据库列名）不会被误处理，除非你自己手写了一个 `name_en`（正常情况下没有理由这么做）。菜单项里的 `name`、分组里新加的 `title` 则是纯展示文本，可以放心加对应的 `_en`。
- 后缀替换只对**字符串值**生效，且要求"基准 key"和"后缀 key"是同一层级的兄弟 key（不支持跨层级）。
- 新增一种语言时（如日语），只需要在 `app/config/app.php` 的 `locale_field_suffixes` 里加一行 `'ja-JP' => 'jp'`，之后就可以在 `CrudConfig.php` 里用 `title_jp`（包括 `getMenus()` 分组里的 `title_jp`）等 key 了，不需要改 `localizeConfig()` 本身。

## 🎨 前端：如何让页面支持多语言

前端分两种场景：**静态 HTML 文案** 和 **JS 动态拼接文案**。

### 场景 1：HTML 里的静态文案 → `data-i18n`

```html
<!-- 之前 -->
<button>退出</button>

<!-- 之后：保留中文作为兜底显示（防止 JS 未加载完成前的短暂闪烁），加 data-i18n -->
<button data-i18n="common.logout">退出</button>
```

页面加载时，`i18n.js` 的 `applyI18n(document)` 会自动扫描所有 `[data-i18n]` 元素并替换为当前语言的文案（用 `innerHTML` 写入，因此翻译文案里允许包含简单的 `<strong>` 等行内标签）。

其他两个变体：

```html
<input data-i18n-placeholder="common.username_placeholder" placeholder="请输入用户名">
<i data-i18n-title="crud.select_icon_title" title="选择图标"></i>
```

### 场景 2：JS 里动态拼接的文案 → `t(key, fallback)`

```js
// 之前
layer.msg('确定删除吗？', { icon: 3 });

// 之后
layer.msg(t('crud.confirm_delete', '确定删除吗？'), { icon: 3 });
```

`t()` 签名：`t(key, fallback)`，`fallback` 是**开发期兜底文案**（当前语言 + zh-CN 基准都找不到 key 时显示），同时也是代码可读性的辅助说明，建议始终传。

### 在哪里维护前端字典？

`public/admin/assets/js/i18n.js` 里的 `I18N_DICT` 常量，按 `zh-CN` / `en-US` 两个顶层 key，再按 section 分组（`common` / `crud` / ...），**结构必须与后端语言包保持同样的风格**（虽然是两套独立的字典，互不影响，但保持风格一致方便维护）。

> **什么文案放前端字典，什么放后端语言包？**
> - 纯粹的**框架外壳/UI 交互文案**（按钮、确认框、占位符等，不涉及业务数据）→ 前端 `i18n.js`
> - **由后端接口动态生成的成功/失败消息**（Controller/Middleware 里的字符串）→ 后端语言包，用 `lang()`
> - **`CrudConfig.php` 里的菜单名、表单 label 等** → 不属于这两者，用字段级多语言后缀（见上文「CrudConfig 字段级多语言」一节），既不进前端字典也不进后端语言包

### 新增/自定义页面（View 模式）里的多语言

View 模式页面是 PHP 服务端渲染，直接在 PHP 里用 `lang()` 即可，无需前端字典：

```php
<?php
// app/views/admin/my-page.php
include __DIR__ . '/_head.php';
?>
<div class="view-title"><?= htmlspecialchars(lang('my_page.title')) ?></div>
```

`currentLocale()` 会通过 Cookie `admin_locale`（`config.js` 的 `setLocale()` 已自动写入）识别当前语言，无需额外处理。

### CRUD 页面里的字段选项（select/radio/checkbox 的 options）

`CrudConfig.php` 里配置的 `options` 数组同样用字段后缀约定（`localizeConfig()` 是递归处理的，嵌套在 `options` 里的 `label`/`label_en` 一样生效）：

```php
'options' => [
```

## 🔀 语言切换器

- **位置**：后台主页（`index.html`）顶部右上角，登录页（`login.html`）右上角。
- **组件**：`renderLocaleSwitcher(containerId)`（`i18n.js`），渲染一个 `<select>`，选项为 中文 / English。
- **切换逻辑**：`switchLocale(locale)` → `setLocale(locale)`（写入 `localStorage` + `Cookie`） → `location.reload()`。

**为什么切换后整页刷新，而不是无刷新替换文案？**

因为一次刷新即可同时保证三类内容都以新语言呈现：

1. 静态 HTML 的 `data-i18n` 文案（`applyI18n()` 会在 `DOMContentLoaded` 时重新执行）
2. 后端返回的菜单 / CrudConfig / 统计数据（`request()` 重新发起时会带上新的 `X-Locale`）
3. `crud-renderer.js` 里当前渲染的表格/表单（重新渲染时会用新语言的 `t()` 结果）

避免了维护"局部重渲染"的复杂状态同步逻辑，牺牲的仅仅是一次页面刷新（几百毫秒），对管理后台这种低频操作完全可以接受。

## ➕ 如何新增一种语言（如日语 `ja-JP`）

1. **后端语言包**：复制 `app/lang/en-US.php` 为 `app/lang/ja-JP.php`，翻译所有 value。
2. **后端配置**：`app/config/app.php` 的 `supported_locales` 加上 `'ja-JP'`；同时在 `locale_field_suffixes` 里加一行 `'ja-JP' => 'jp'`（用于字段级后缀约定，见上一节）。
3. **前端**：
   - `public/admin/assets/js/config.js` 的 `SUPPORTED_LOCALES` 数组加上 `'ja-JP'`
   - `public/admin/assets/js/i18n.js` 的 `I18N_DICT` 加一个 `'ja-JP': { ... }` 顶层 key（复制 `en-US` 结构翻译）
   - `renderLocaleSwitcher()` 函数里的 `<select>` 加一个 `<option value="ja-JP">日本語</option>`
4. 完成，无需修改其他任何文件——所有业务模块只要用了 `lang()` / `t()` / `title_jp` 后缀，新语言会自动生效，包括 `getMenus()` 里的分组标题（给每个分组加一个 `title_jp` 字段即可，和其他字段后缀完全一样）。（`CrudConfig.php` 里已有的 `_en` 字段不受影响，日语缺失时会保留默认语言原文，不会报错）

## ✅ 开发自查清单（Checklist）

新增或修改后台功能时，请确认：

- [ ] `CrudConfig.php` 里的文案（菜单、`title`/`label`/`text`/`placeholder`/`tip` 等）用**字段后缀约定**（如 `label_en`），**不要**为它们新建 `lang()` key
- [ ] Controller / Middleware 里的动态消息（成功/失败提示、校验错误）用 `lang()`，新增的 key 在 `app/lang/zh-CN.php` 和 `app/lang/en-US.php` 里都存在，且路径完全一致
- [ ] 前端交互文案（不经过后端接口）用 `t()`（JS），维护在 `i18n.js` 字典里
- [ ] 纯技术性内容（字段名 `name`/`field`、图标类名、URL、枚举值本身）**不需要**翻译，也不要给它们加 `_en` 后缀
- [ ] 切换语言（点右上角切换器）后自测一遍功能，确认新语言下页面无异常、无空白文案，且接口响应里没有残留 `_en` 字段

## ❓ 常见问题

### Q1：为什么页面上显示的是 `products.stock_not_enough` 这样的原始 key，而不是文案？

**A**：说明 `zh-CN.php`（基准语言包）里没有这个 key（可能是拼写错误，或者忘了加）。`lang()` 找不到 key 时会直接返回 key 本身，方便快速定位问题——这是有意设计的行为，不是 bug。

### Q2：中英文的语言包 key 结构不一致会怎样？

**A**：`en-US.php` 比 `zh-CN.php` 少的 key，会自动回退显示中文（不会报错，但英文用户会看到中文，属于翻译遗漏）。`zh-CN.php` 缺失的 key 会直接返回 key 字符串本身。建议养成"先加中文、马上补英文"的习惯。

### Q3：能否让不同管理员使用不同的默认语言（存到数据库）？

**A**：当前实现是纯前端持久化（`localStorage` + `Cookie`），未与管理员账号绑定。如果需要"记住该管理员的语言偏好"，可以在登录成功后：
1. 给 `og_admin` 表加 `locale` 字段
2. 登录接口 `AuthController::login()` 里把 `admin['locale']` 一起返回
3. 前端登录成功后调用 `setLocale(res.data.locale)`
4. 用户在设置页修改语言偏好时，同步调用一个新接口写回数据库

这个框架的 `lang()` / `currentLocale()` 机制不需要改动，只是多了一个"服务端记住偏好"的持久化层。

### Q4：前端 `t()` 和后端 `lang()` 是两套独立的字典，会不会不同步？

**A**：是的，故意设计为两套独立字典：前端字典管"纯 UI 交互文案"，后端语言包管"业务/接口返回文案"。两者职责不重叠（参考上文"什么文案放前端字典，什么放后端语言包"一节），所以不存在需要同步的问题。如果发现同一句文案两边都写了，说明其中一处放错了位置，应删除冗余的那份。

### Q5：Worker 模式下会不会出现语言错乱（A 用户的语言被 B 用户看到）？

**A**：不会，这一点在实现时特别处理过。`app/helpers/i18n.php` 在 Worker 模式下只在进程启动时 `require` 一次，所以 **`currentLocale()` 故意没有使用 `static` 变量缓存探测结果**——每次调用都重新从当前请求的 Header / 查询参数 / Cookie 探测，避免复用上一个请求（可能是别的管理员）探测到的语言。

唯一使用 `static` 缓存的是 `loadLangPack()`（按 `locale` 缓存语言包**文件内容**），这是安全的，因为语言包文件内容在进程运行期间不会变化，跨请求复用没有副作用，反而能减少重复的文件 IO。

同理，`localizeConfig()` 用到的 `i18nAllFieldSuffixes()` 也用了 `static` 缓存，缓存的是 `locale_field_suffixes` 这份**静态配置**本身（不是探测结果），同样没有跨请求污染问题。

### Q6：用 CRUD 设计器（`crud-designer.html`）生成/修改模块后，我手写的 `_en` 字段会不会被覆盖掉？

**A**：视操作类型，有风险，保守起见一律当作"会"处理。CRUD 设计器目前**不识别**字段级多语言后缀：

- 分组级操作（改图标、改展开状态、重命名分组）：设计器是就地修改已加载的分组对象，`title_en` 等未识别字段大概率会被保留；但**重命名分组**只会改 key，不会同步改 `title`/`title_en`，需要手动同步。
- 表单/表格逐个字段的可视化编辑（新增字段、编辑字段属性）：设计器很可能按它认识的 schema 重新构造该字段对象，`_en` 后缀字段会丢失。

约定：**任何模块一旦手工加了多语言后缀字段，后续该模块的调整就应该直接改 `CrudConfig.php` 源码，不要再用设计器保存覆盖**。这是有意的取舍——比起给设计器改造出支持任意语言数量的多语言编辑 UI（收益低、改动大），手动维护配置文件的成本更低。

> 历史踩坑：最早给 `getMenus()` 分组标题用的是"按 `currentLocale()` 动态计算 key"的写法（一个闭包），结果设计器通过 PHP 反射读取配置时会直接**执行**这个闭包，当场塌缷成一个具体语言的字符串，保存后多语言能力永久丢失。这也是为什么整套机制被设计成**纯静态字面量数组**（`_en` 后缀、`title`/`title_en`）——只有静态数据才能在"读取 → 设计器编辑 → 保存覆盖文件"的过程中被完整保留。
